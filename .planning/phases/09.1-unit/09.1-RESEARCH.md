## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** 交付单位 = 合并 unit：合并后的一组镜头共用一个翻拍视频，用户直接对整个 unit 审核 / 采用 / 备注，不把生成视频裁剪回单个 shot。 — **Reversibility:** one-way — 数据模型需新增 unit 粒度，Phase 11 完整性检查/导出合同需同步改为 unit 级
- **D-02:** 合并方式 = 纯手动：系统不做默认自动合并，只在用户主动把 >= 2 个镜头加入同一个 unit 时才合并生成。 — **Reversibility:** reversible
- **D-03:** ~~合并方向 = 优先同构相邻镜头~~ **已取消**：不做基于 sceneTag/characterTags 的同构判定与合并建议；合并目标完全由用户手动选择（本次讨论变更）。
- **D-04:** 一个 Shot 只允许属于唯一 unit：某 Shot 一旦加入某 unit，即归属该唯一 unit，不可同时挂到多个 unit；已加入 unit 的 shot 不能再单独生成视频。 — **Reversibility:** one-way — 需在 `RemakeVideoUnitMember.shotRevisionId` 上加唯一约束并迁移既有数据
- **D-05:** MVP 不处理超长镜头：unit 总长上限按现有模型上限（15s）行为一致——超出上限不做自动拆段，只要求用户拆组/接受拉长；超过 15s 的单个长镜头不在本设计范围。
- **D-06:** 每镜头只保留一个关键帧：组内每个镜头贡献 1 张 adopted 关键帧（默认取 middle / 最忠实画面的那帧），作为该镜头时间段画面锚；N 镜头传 N 张，按 sequence 顺序。N 张关键帧 + 合并动作表 + 去重资产必须 ≤ `content[]` 图上限 9。
- **D-07:** 动作表合并为一张六宫格 / 九宫格大图：复用/扩展 Phase 8 的 `renderActionSheet`，把 unit 各镜头按 sequence 顺序铺进 6/9 宫格（每格 = 一镜头的一帧 + 镜头编号），存为 unit 级 action_sheet 输出版本。
- **D-08:** 角色 / 场景 / 物品 / 语音跨镜头去重并入：按 asset id 去重，同一角色只入一次；超上限按关键帧 > 动作表 > 角色 > 场景 > 物品 > 语音降级（音频 cap=3）。
- **D-09:** 提示词合并为一条带时间锚点的分镜时间表：各镜头 adopted Video Prompt 合并为一条，逐镜头标注累计时间区间（如 `0-1s 镜头1；1-4s 镜头2`），头部声明多镜头 cut 切换、非连续运镜；时间区间按成员时长占比缩放适配归一化后的总时长。 — **Reversibility:** costly — 涉及提示词模板与时间锚点纯函数，调用面广但可回退
- **D-10:** 契约调整：现有 `assertVideoReferencesHaveKeyframe` 只认 `*_keyframe`(start/middle/end)，unit 需在 `reference-roles.ts` 扩展每成员角色（如 `shot_keyframe`）或调整排序/抽查函数。
- **D-11:** 允许单独生成兜底：短镜头可以不进 unit，单独生成时按现有 `deriveDefaultVideoDuration` 逻辑拉长到最短档（如 4s）。
- **D-12:** UI 明确标注拉长：单独生成的短镜头在成片页标注"拉长到最短档"，用户清楚知道时长被注水。
- **D-13:** 兜底提示词不声明扩展：单独生成兜底时不加"原时长 vs 生成时长"的特殊说明，保持简单。
- **D-14:** 入口 = 单 shot 页内勾选切 unit：成片页顶部保持单 shot 视图，另加"合并 unit 模式"入口；用户勾选多个镜头后进入 unit 视图。
- **D-15:** 成员任意组合：unit 成员不要求相邻（sequence 连续），允许任意镜头组合；用户自己负责顺序合理性，提交时按勾选顺序生成。
- **D-16:** 完整预览面板：unit 视图展示成员镜头顺序列表（含时长）+ 参考图顺序预览（每镜头 1 帧 + 合并动作表大图）+ 时间锚点提示词预览 + 总时长/参数，提交前所见即所得（对齐 VGEN-02 / D-05 语义）。
- **D-17:** unit 级版本闭环：unit 有独立版本列表，沿用现有 batch/version/采用/备注/失效语义；播放 unit 整段视频，采用指针在 unit 级。
- **D-18:** 成员状态 = 显示 unit 归属并可跳回：已加入 unit 的成员在单 shot 视图显示"由 unit 交付"，视频区隐藏/禁用单 shot 生成，点击可跳回 unit 视图。
- **D-19:** 提交前可调、提交后冻结：提交前可增删/重排成员，提交生成后 unit 成员冻结（不可改，只能重新生成或重建 unit）。
- **D-20:** 时长不足提示：系统保留"镜头过短（< 最短档），建议并入相邻镜头或接受拉长"的提示引导，但不自动指定合并目标（取代原同构建议）。
- **D-21:** unit 组内任一成员缺少已采用关键帧 / 已批准 Video Prompt / 合法参数时，阻止该 unit 生成并逐成员说明原因。
- **D-22:** unit 输入快照沿用不可变冻结 + `videoInputFingerprint` 去重语义；任一成员/时间锚变化会改变指纹；上游（Prompt/关键帧）变化利用现有 provenance/invalidation 传播到 unit 版本复核状态（对齐 D-17 语义，作用范围是 unit）。

## Summary

本阶段在 Phase 9 单 shot 视频生成闭环上叠加一个**跨 shot 的 unit 粒度**：用户手动勾选 2+ 个镜头组成 unit，系统为每个成员收集 1 张 adopted 关键帧 + 合并动作表大图 + 按 asset id 去重的资产，合并为一条带时间锚点的分镜时间表提示词，复用现有视频队列 / Worker / 模型网关 / COS 存储路径一次生成整段 unit 视频，并建立 unit 级 batch/version/采用/备注/失效闭环。核心约束是外发模型 `content[]` **图上限 9 / 音频上限 3**（`REMAKE_VIDEO_IMAGE_CAP=9` / `REMAKE_VIDEO_AUDIO_CAP=3`，[VERIFIED: `src/lib/remake-projects/video/reference-plan.ts:23-24`]），因此跨镜头参考必须"每镜头 1 帧 + 合并动作表大图 + 资产去重"，不能全量传递。

**最重要的研究发现：**

1. **单 shot 管线可 1:1 平行扩展**：`buildVideoGenerationSubmission` → `buildRemakeVideoTaskDescriptor` → `handleRemakeVideoTask` → `appendVideoGenerationBatch` 是一条完整、解耦、可复制的链路。unit 版只需替换"输入快照 schema + 参考收集 + 提示词模板"，提交、冻结、指纹、去重、持久化、失效传播全部复用。[VERIFIED: `src/lib/remake-projects/video/service.ts:305-465`; `src/lib/remake-projects/video/task-contract.ts:35-59`; `src/lib/workers/handlers/remake-video.ts:50-114`]
2. **多镜头参考范式已经存在**：`buildShotGroupArkContentPlan`（composite 大图 + content[] 多参考 + @Image/@Audio 后缀）与 unit 差异仅在参考来源——unit 用"每镜头 1 关键帧 + 合并动作表"而非"一张 composite + 每镜头 item 图"。[VERIFIED: `src/lib/workers/video.worker.ts:485-583`]
3. **时间码是字符串、时长是数字，且前端 `durationSeconds` 当前存在真实缺口**：`startTimecode`/`endTimecode` 是 `MM:SS.mmm`/`HH:MM:SS.mmm` 字符串（`z.string()`），`duration` 是数字秒；snapshot 的 `timeRange` 直接透传字符串，而 adapter 的 `durationSeconds` 只在 `typeof start === 'number'` 时计算差值，否则**回退 3**——当前所有 shot 的 `durationSeconds` 实际都是 3s。D-09 的时间锚点提示词必须先在 snapshot 层补齐"每成员时长（数字秒）"，否则时间区间无真实依据。[VERIFIED: `src/lib/remake-projects/scenedetect/contracts.ts:13-15,54-57`; `src/lib/remake-projects/service.ts:249-252`; `src/lib/remake-projects/keyframes/adapter.ts:193-195`]
4. **unit 模型不破坏现有 `@@unique([shotRevisionId])`**：现有 `RemakeVideoTrack` 唯一约束保留不动；新表 `RemakeVideoUnitMember` 的 `@@unique([shotRevisionId])` 是独立约束，与 track 无冲突。"已入 unit 的 shot 不能再单独生成"是应用层门禁（D-04/D-18），不是 DB 约束。[VERIFIED: `prisma/schema.prisma:773-788`]
5. **契约收紧点是角色枚举与顺序**：`assertVideoReferencesHaveKeyframe` 用 `role.endsWith('_keyframe')` 判定，`assertVideoReferenceOrder` 用 `VIDEO_REFERENCE_ROLE_ORDER` 单调递增判定——unit 新增 `shot_keyframe` 角色后必须同步扩展角色表、顺序表、label/usage 映射与抽查函数，否则 D-06 的 N 张关键帧会因同角色重复而触发 `REMAKE_VIDEO_REFERENCE_ORDER_INVALID`。[VERIFIED: `src/lib/remake-projects/video/contracts.ts:77-99`; `src/lib/remake-projects/video/reference-roles.ts:21-47`]

**Primary recommendation:** 新增 `RemakeVideoUnit` / `RemakeVideoUnitMember`（`@@unique([unitId, ordinal])` + `@@unique([shotRevisionId])`）与独立 unit 交付容器（推荐单建 `RemakeVideoUnitTrack`，或为 batch/version/adoption 增加 `trackType` 多态），平行复制 `video/` 目录的 contracts/task-contract/service/reference-plan 链路为 unit 版；时间锚点计算与合并动作表渲染作为纯函数 + 确定性 Sharp 渲染；成片页 `RemakeVideoStage` 增加"合并 unit 模式"入口与 unit 预览/版本面板。

### Pattern 1: 平行复制单 shot 链路（service → task-contract → worker → append）

**What:** `buildVideoGenerationSubmission`（[VERIFIED: `service.ts:305-465`]）的每个阶段在 unit 版中都有对应物：项目/当前 revision 校验 → 门禁（D-03 单 shot / D-21 逐成员）→ 模型解析（project > user）→ capability 归一化 → 参考收集 → `buildRemakeReferencePlan` → 指纹 → 任务描述符。worker 端 `handleRemakeVideoTask`（[VERIFIED: `remake-video.ts:50-114`]）的 preflight/进度/生成/上传/持久化五段流程可原样复用，仅替换快照解析与 append 目标。

**When to use:** unit 提交、unit 任务执行。差异集中在输入收集与提示词，不在队列/网关/存储。

### Pattern 2: 参考角色扩展与顺序契约

**What:** `VIDEO_REFERENCE_ROLES`（[VERIFIED: `reference-roles.ts:21-30`]）与 `VIDEO_REFERENCE_ROLE_ORDER`（[VERIFIED: `reference-roles.ts:38-47`]）是 `orderedVideoReferenceSchema`、`assertVideoReferenceOrder`（[VERIFIED: `contracts.ts:87-99`]）、`buildRemakeReferencePlan`（[VERIFIED: `reference-plan.ts:85-107`]）和 `buildRemakeReferencePromptSuffix`（[VERIFIED: `reference-plan.ts:135-195`]）的共同契约。unit 需要 `shot_keyframe`（每成员 1 个，按 ordinal 排序）→ `action_sheet`（合并大图）→ 资产。扩展点：新增 `'shot_keyframe'` 角色并把 `assertVideoReferencesHaveKeyframe` 的判定从 `endsWith('_keyframe')` 扩展为同时接受 `shot_keyframe`；顺序判定改为允许同角色连续出现（N 张成员关键帧 ordinal 递增即可）。

**When to use:** D-06/D-10 落地。注意 `buildRemakeReferencePlan` 按 `VIDEO_REFERENCE_ROLE_ORDER` 排序——多个 `shot_keyframe` 同权时用稳定排序保序，或先按 ordinal 排好再入 plan。

### Pattern 3: 追加历史 + 显式采用 + 幂等批次的持久化

**What:** `appendVideoGenerationBatch`（[VERIFIED: `service.ts:538-617`]）的事务模式：`trackId_operationKey` 唯一幂等 → 创建 batch（冻结 `inputSnapshot`/`modelOptions`/`orderedReferences` JSON 深拷贝）→ 创建 version + `outputVersion`（`fingerprint: ${operationKey}:${inputFingerprint}:1`）→ `remakeProvenanceRecord`。unit 版按相同模式落到 unit track/batch/version。

**When to use:** unit 生成成功后的持久化。`RemakeVideoUnitMember` 冻结（D-19）在提交时写入 unit 表，batch 快照中同时保留成员稳定 key。

### Pattern 4: 上游失效传播（D-17/D-22）

**What:** `invalidateRemakeVideoVersions`（[VERIFIED: `video/invalidation.ts:11-113`]）按 shot 找失效输出 → 扫当前 revision 的 track.batches 的 `orderedReferences.mediaId` → 命中则标记 outputVersion `needs_review` + 幂等建 invalidation。unit 版需要：unit batch 的 `orderedReferences` 同样含成员关键帧/动作表/资产的 mediaId，扫 unit batch 即可；另需在任一成员 shot 的 Prompt/关键帧失效时把整个 unit 的版本标记复核（D-22）。

**When to use:** keyframe/action_sheet/prompt invalidation 路径（`keyframes/invalidation.ts:60-66` 已调用视频失效）扩展到 unit。

### Anti-Patterns to Avoid

- **复用单 shot track 挂 unit**：`RemakeVideoTrack @@unique([shotRevisionId])` 是"每 shot 一 track"，unit 是跨 shot 粒度——不要尝试在现有 track 上表达多成员，会破坏唯一约束语义并污染单 shot 通路。[VERIFIED: `schema.prisma:785`]
- **前端算时间锚点、服务端另算一套**：D-16 要求所见即所得，时间锚点纯函数必须前后端共用同一实现（提交前返回给前端预览，提交时冻结进快照）。[VERIFIED: `09.1-CONTEXT.md` D-16/D-22]
- **直接拼接成员 prompt 段落**：D-09 要求"带时间锚点的分镜时间表 + 头部 cut 声明"，不是简单 `\n` 拼接；拼接会让模型把多镜头当连续运镜。[VERIFIED: `remake-video-merge-unit-design.md:141-162`]
- **成员角色不加区分全用 `start_keyframe`**：`assertVideoReferenceOrder` 要求角色顺序单调递增，同角色会触发 `REMAKE_VIDEO_REFERENCE_ORDER_INVALID`。[VERIFIED: `contracts.ts:87-95`]

## Common Pitfalls

### Pitfall 1: `durationSeconds` 前端恒为 3（现有缺口，unit 时间锚点无依据）
**What goes wrong:** `timeRange` 透传字符串 timecode，adapter 只在 `typeof start === 'number'` 时计算，否则回退 `3`——当前所有 shot 的 `durationSeconds` 都是 3。[VERIFIED: `service.ts:249-252`; `adapter.ts:193-195`]
**Why it happens:** snapshot 未投影 `payload.duration`（数字秒），且无 timecode→seconds 解析。
**How to avoid:** 在 remake snapshot 投影中新增数字秒时长（解析 `startTimecode`/`endTimecode` 或直接投影 `payload.duration`），adapter 优先取数字时长；unit 时间锚点纯函数以数字秒为准。
**Warning signs:** 成片页所有镜头时长显示 3.0 秒；unit 预览时间区间与镜头实际时长不符。

### Pitfall 2: 同角色多张关键帧触发顺序契约报错
**What goes wrong:** N 个成员的 `shot_keyframe` 若用同一 role，`assertVideoReferenceOrder` 的 `>=` 检查抛 `REMAKE_VIDEO_REFERENCE_ORDER_INVALID`。[VERIFIED: `contracts.ts:87-95`]
**How to avoid:** 顺序契约改为"角色组内允许连续 + ordinal 递增"，或在 `buildRemakeReferencePlan` 稳定排序后跳过排序断言、只查 ordinal。
**Warning signs:** unit 提交 500，错误码 `REMAKE_VIDEO_REFERENCE_ORDER_INVALID`。

### Pitfall 3: 跨成员资产重复顶满 9 图上限
**What goes wrong:** 同角色/场景在多镜头反复出现，不去重则 N 镜头 + 动作表 + 资产很快超过 9 图。[VERIFIED: `09.1-CONTEXT.md` D-08]
**How to avoid:** 全成员收集后按 assetId 去重（Set），再走 `buildRemakeReferencePlan` 截断。
**Warning signs:** 预览参考数 > 9；模型报参考过多错误。

### Pitfall 4: unit 成员冻结与唯一归属被绕过
**What goes wrong:** 已入 unit 的 shot 仍可单独提交视频（D-04/D-18），或提交后成员仍可增删（D-19）。
**How to avoid:** 服务端在单 shot 提交入口检查 `RemakeVideoUnitMember` 归属并拒绝；unit 提交事务内冻结成员集合；UI 侧隐藏/禁用单 shot 生成并显示"由 unit 交付"。
**Warning signs:** 单 shot API 对已入 unit 的 shot 仍返回 202。

### Pitfall 5: 时间锚点提示词缩放后区间不闭合
**What goes wrong:** 各段区间之和 ≠ 实际生成时长（归一化到档位值 T 后），模型时间锚与视频对不上。
**How to avoid:** 时间锚点纯函数按 `memberDur / ΣmemberDur × T` 缩放并断言 `Σ区间 = T`；前端预览与提交冻结用同一函数（D-16）。[VERIFIED: `remake-video-merge-unit-design.md:176`]
**Warning signs:** 预览总时长与提交后 batch 的 durationSeconds 不一致。

### Pitfall 6: 合并动作表失去 provenance
**What goes wrong:** 只存 unit 动作表 URL，无法追溯由哪些成员、哪些关键帧合成。
**How to avoid:** 仿 `persistActionSheet`（`@@unique([revisionId, kind, fingerprint])`）存 unit 级 `action_sheet` outputVersion + `remakeProvenanceRecord`，记录成员顺序与来源 mediaId。[VERIFIED: `action-sheet.ts:71-95`; `schema.prisma:569`]
**Warning signs:** unit 版本详情无法展示"合并动作表由哪些镜头构成"。

### 现有时间码解析（可复用/统一）— vendor 与 storyboard 两处

```ts
// src/vendor/scenedetect/utils/timecode.ts:34-48 — "HH:MM:SS.mmm" / "MM:SS.mmm" / "SS.mmm" → frame
export function timecodeToFrame(timecode: string, fps: number = 30): number {
  if (!timecode) return 0;
  const parts = timecode.split(':');
  let seconds = 0;
  if (parts.length === 3) {
    seconds = parseInt(parts[0], 10) * 3600 + parseInt(parts[1], 10) * 60 + parseFloat(parts[2]);
  } else if (parts.length === 2) {
    seconds = parseInt(parts[0], 10) * 60 + parseFloat(parts[1]);
  } else {
    seconds = parseFloat(parts[0]);
  }
  return Math.max(0, Math.round(seconds * fps));
}
```

```ts
// src/lib/novel-promotion/storyboard-package/mapper.ts:123-138 — 区间字符串 → {start,end} 秒（无 fps 依赖）
function parseTimecodePart(part: string | undefined) {
  if (!part) return 0
  const pieces = part.split(':').map((piece) => Number(piece))
  if (pieces.some((piece) => !Number.isFinite(piece))) return 0
  if (pieces.length === 3) return pieces[0] * 3600 + pieces[1] * 60 + pieces[2]
  if (pieces.length === 2) return pieces[0] * 60 + pieces[1]
  return pieces[0] || 0
}
```

**建议：** 在 remake 域新增纯函数 `timecodeToSeconds(timecode: string): number`（合并以上两种格式，支持 `MM:SS.mmm` / `HH:MM:SS.mmm` / 纯秒），单测覆盖；或复用 `timecodeToFrame` 除以 fps（需从 vendor 导出，注意 vendor 边界）。[ASSUMED — 具体位置属 discretion]

### 时间锚点提示词模板（D-09 目标形态）

```ts
// 纯函数：输入成员 (ordinal, durationSeconds, adoptedPrompt) + 归一化总时长 T
function buildUnitTimedPrompt(members, totalDurationSeconds: number) {
  const sum = members.reduce((acc, m) => acc + m.durationSeconds, 0)
  const scale = sum > 0 ? totalDurationSeconds / sum : 1
  let cursor = 0
  const lines = members.map((m, i) => {
    const start = cursor
    const end = cursor + m.durationSeconds * scale
    cursor = end
    const fmt = (s: number) => `${Math.round(s * 10) / 10}s`
    return `${fmt(start)}-${fmt(end)}（镜头 ${i + 1}）：${m.adoptedPrompt}`
  })
  return [
    '这是按时间顺序切换的多镜头视频，各镜头之间为剪接切换（cut），不是连续运镜。',
    `总时长约 ${totalDurationSeconds} 秒。各镜头的时间位置与提示如下：`,
    ...lines,
  ].join('\n')
}
```

## Open Questions

1. **unit 输入快照中 `promptVersionId` 语义**

   - Recommendation: unit 版聚合收集缺项并逐成员返回（如 `REMAKE_VIDEO_UNIT_MEMBER_MISSING:${ordinal}:KEYFRAME`），前端按成员渲染（对齐 D-21 语义）。
